5. **0.3 不是 C# 的 `0.3d`**。`[0x7446F0]` 是 64 位尾数的 x87 extended，严格小于 0.3；

   （`BigMul(|dmg|, 0x9999999999999999) >> 1`），实测 0..200000 全区间零失配，
   而 `(int)(damage * 0.3d)` 每逢 10 的倍数就错一档。
6. **连击衰减的首拍不衰减**：超过 3000 ms 的那一拍走 `0x7446C0`，只把计数清 0、
   **不查表**。所以序列是 100%(首) → 100%(表[0]) → 80% → 40% → 20% → 10% → 10%…
7. **上下限**：整条链**没有任何钳位**，没有 `max(dmg,1)`，也没有上限。
   目标等级 ≥150 时 `min(150, 等级)` 与 `等级/150` 两处各自饱和，仅此而已。

## 4. magic 65 / 66 / 67 / 68 定性与顺序依赖

### 4.1 四者是什么

外层施放阶梯 `sub_6BC6xx`：`0x6BC71E sub eax,0x41 / je 0x6BC9FE`（65），
`0x6BC727 sub eax,3 / je 0x6BCAC4`（68）；DoSpell TABLE2 的 `0x6ED839` 与 `0x6ED83D`
**两个槽持同一个 dword `0x6EDE39`**，即 66 与 67 共用一份指令流。

| id | 入口 | 语义 | 本端 |
|---|---|---|---|
| 65 | `0x6BC9FE` | **蓄力**：置 `[+0xE8] = 1`、发 `SM_CHARGED_COUNTER`；冷却键取缓存记录 id | `TryActivateNativeSkill65Charge` |
| 66 | `0x6EDE39` → `sub_745744` | **释放**：`[vmt+0x4C]` 出伤害 → 练级 → `sub_76FE44` 排队单体效果（600 ms，range 2） | `TryActivateNativeSkill66Or67` |
| 67 | 同 66（同一 dword 槽） | 同 66 | 同上 |
| 68 | `0x6BCAC4` | **冲锋**：跑道位移 + 沿途 `[vmt+0x4C]` 出伤害经 `0x771AD4/0x771AEC` 落地 | `TryActivateNativeSkill68Charge` |
| — | `0x772388` | **动作 1017**（本轮）：第五个消费者，射程 2 格 | `RunNativeAction1017Swing` |

`[+0xE8]` 由 65 置 1、由 `0x74439C` 清 0；全镜像找不到读点，故本端保留写序但不作判据。

### 4.2 顺序依赖 —— 验证结论：**存在，而且本端已如实复现**

写点普查：`89 8B/86 C4 00 00 00` 形态全镜像 9 处，落在技能刷新器里的**只有一处**
`0x76B170`。它所在的臂由

```
0x76AF2B  83 C0 F9    add eax,-7
0x76AF2E  83 E8 04    sub eax,4
0x76AF31  0F 82 ..    jb 0x76B16D          ; ★ 无符号借位 => (id - 65) < 4，即 65..68
```

选中，而外层是一个**顺序**遍历：

```
0x76AE37  edi := List.Count / dec / jl 尾 / inc
0x76AE4E  loop: item := List[[ebp-0xC]]          ; TList.Get = 0x424D4C
0x76AE6B        id := MagicId(item)              ; 0x4C853C
          ... 各臂 ...
0x76B2FE  inc [ebp-0xC] / dec edi / jne 0x76AE4E
```

三项事实合起来就是顺序依赖：

1. `0x76B170 mov [ebx+0xC4],eax` 是**无条件覆盖**，臂内没有任何「已有就不写」的判断；
2. 遍历严格按 `m_MagicList` 的**列表顺序**，所以**列表里最后出现的那个 65..68 记录赢**；
3. 全镜像**没有任何一处把 `[+0xC4]` 写回 0**（9 个写点里 8 个属别的结构），
   所以一旦缓存就永久保留，下线重登后按重建的列表顺序重新决出。

可观测后果（`0x744388` 的 `case key of` 用的是**缓存 id**，不是所施放的 id）：

- 同时学了 66 与 67、列表里 67 在后 → 施放 **66** 也会走 **SC**（67 的属性对），
  并占用 **67** 的冷却键。本端注释（`NativeSkill66Or67.cs:38-41`）早已把这条记下。
- 65/66/67/68 与动作 1017 五个入口**共用同一把 45 秒锁**，因为键只有一个。
- 缓存记录若指向 65 或 68，而玩家施放 66/67 释放，属性对会变成 DC 或第四对。

**「四者能否同时习得」**：本底本**不存在任何互斥**——`m_MagicList` 是逐条独立记录，
刷新器对四个 id 用同一条臂而不是四条互斥臂，学习路径上也没有查重。
是否真的同时出现取决于 `Magic.DB` 的内容，**那不在镜像里，无法用字节裁决**。
结论按证据分层：**机制层面顺序依赖确凿存在且已复现；触发它需要 ≥2 个 65..68 同时在册，
这一前提由服务器配置决定，本轮不臆断。**

本端复现的忠实性（`TBaseObject.cs:3086-3159`）：
`for (i = 0; i < m_MagicList.Count; i++)` 顺序遍历 ✓；
`case 65: case SKILL_66: case SKILL_67: case 68: m_NativeChargedCounterMagic = UserMagic;`
四标签共用一臂、无条件覆盖 ✓；无任何清点 ✓；
选择子 `UserMagic.wMagIdx` —— 全仓每一处赋值都是 `wMagIdx = magic.wMagicID`，
与原生 `sub_4C853C` 同源 ✓。
