### 1.1 先复核，四条全部成立，另外纠正一处口径

上一轮给的四字段结论**全部正确**，但下发槽写的是 `+0x250`，实际是 `+0x254`。这不影响字段，
但影响"下发点唯一性"的论证方式，必须说清楚。

`+0x254` 是 `+0x250` 的**裸缓冲区孪生体**，不是别的通道：

## 3. 任务二：四项 BLOCKED 全部推进

### 3.1 B2 —— SM 56 的 24 字节记录布局：**解出**

SM 56 与 SM 54 在同一个函数 `SendMapDescription`（`0x6E37C4`）里。它不是"一个包带一张表"，
而是**三阶段列表推送**，三个下发点全部在这个函数内：

| 阶段 | VA | 槽 | Recog | Param | Tag | Series | 正文 | 门 |
|---|---|---|---|---|---|---|---|---|
| 清空 | `0x6E388D` | `+0x250` | 0 | **0** | 0 | 0 | 空 | `0x6E3872 cmp byte [ebx+0x9BC],0 / je` |
| 逐条 | `0x6E38E7` | `+0x254` | 0 | **1** | 0 | 0 | **24 字节裸记录** | 链表非空，`[node+0x18]` 为 next |
| 结束 | `0x6E3914` | `+0x250` | 0 | **2** | 0 | 0 | 空 | `0x6E38F9 cmp byte [ebx+0x9BC],0 / je` |

逐条那一发的字节：

```
006E38CB  8B75F4         mov esi,[ebp-0xC]      ; 当前节点
006E38CE  8B4618         mov eax,[esi+0x18]     ; next
006E38D4  6A01           push 1                 ; Param  = 1
006E38D6  6A00 6A00      push 0 / push 0        ; Tag = Series = 0
006E38DA  56             push esi               ; Buffer = 节点本体
006E38DB  6A18           push 0x18              ; BufLen = 24
006E38DD  33C9           xor ecx,ecx            ; Recog  = 0
006E38DF  66BA3800       mov dx,0x38
006E38E7  FF9654020000   call [VMT+0x254]
```

**记录布局**，从构造点 `0x697695` 反出来（`mov eax,0x1C / call 0x402FA0` = GetMem(28)）：

| 偏移 | 宽度 | 来源 | 指令 |
|---|---|---|---|
| +0x00 | 15 | ShortString[14]，长度字节 + 最多 14 个 GBK 字节（7 汉字） | `0x6976BE mov cl,0x0E` / `call 0x4039E4` |
| +0x0F | 1 | `StrToIntDef(token6,0)` | `0x6976CF mov [ebx+0x0F],al` |
| +0x10 | 2 | `StrToIntDef(token2,0)` | `0x6976DC mov [ebx+0x10],ax` |
| +0x12 | 2 | `StrToIntDef(token3,0)` | `0x6976EA mov [ebx+0x12],ax` |
| +0x14 | 4 | `call 0x4C79BC(token5)` | `0x6976F8 mov [ebx+0x14],eax` |
| = 0x18 | 24 | **上线部分到此为止** | |
| +0x18 | 4 | next 指针，**不上线** | `0x695648` 追加 |

`0x4039E4` 是 LStr→ShortString，字段宽度 = `1 + cl`。这条独立验证过：`0x6D3694` 里
同一个函数以 `cl=0x0A / 0x14 / 0x0F / 0x0F` 往缓冲区偏移 `0 / 0x0B / 0x20 / 0x30` 写，
间距恰好 11 / 21 / 16，即 `1+cl`。

**数据源 = `\Config\MapDesc.Dat`**（字面量 `0x6977A8`，长度 19，
`5C 43 6F 6E 66 69 67 5C 4D 61 70 44 65 73 63 2E 44 61 74`；缺文件时走
`0x69772E` 拼 `0x6977C4 "找不到文件："` 报错）。行格式：`;` 开头是注释
（`0x69751A cmp byte [eax],0x3B`），分隔符是 `空格 / TAB / , / ;` 四个
（`0x697529..0x697535` 写 `0x20 09 0x2C 0x3B`，`push 3` = High(array)）。
六个 token 依次落到 `[ebp-0x10/-0x14/-0x18/-0x1C/-0x20/-0x24]`，其中
token1 是索引键（`0x697657` 拿去查 `[Self+0x50]`），token4 是记录里的名字，
token2/3 是两个 word，token5 是 dword，token6 是 byte。token1 或 token6 为空则整行丢弃
（`0x69763D` / `0x697647`）。

### 3.2 B1 —— SM 54 的子区域描述容器：**解出**

`0x77B5CC(eax=PEnvir, dx=x, cx=y, [ebp+8]=out)`：

```
0077B5E4  8B5248     mov edx,[PEnvir+0x48]    ; 默认描述
0077B5E7  E8689FC8FF call 0x405554            ; out := 默认
0077B5EC  6685DB 743F test bx,bx / je done    ; x==0 -> 用默认
0077B5F1  6685F6 743A test si,si / je done    ; y==0 -> 用默认
0077B5F9  8B4024     mov eax,[PEnvir+0x24]    ; 子区域链表头
0077B60C  E8C70C0000 call 0x77C2D8            ; node.Contains(x,y)
0077B61A  E8A10C0000 call 0x77C2C0            ; out := node.Description
0077B624  8B400C     mov eax,[node+0x0C]      ; next
```

所以：**`[PEnvir+0x48]` 是地图默认描述**（= C# 现在用的 `m_PEnvir.sMapDesc`，这一半是对的），
**`[PEnvir+0x24]` 是子区域链表**（节点 next 在 `+0x0C`，命中判定 `0x77C2D8`，取串 `0x77C2C0`），
**x 或 y 为 0 直接短路到默认**——这正是 SM 56 那段用 `(0,0)` 调它来取"地图级描述"的原因。

C# 完全没有 `[PEnvir+0x24]` 这个容器，所以站在子区域里时会发地图默认描述而不是子区域描述。

另外注意 SM 56 的触发字段是 **`[PEnvir+0x44]`**（`0x6E3848 mov edx,[edx+0x44]`），
与 `+0x48` 是两个不同的串，别混。

### 3.3 B4 —— 数据驱动转发点 `0x76CC44`：**解出**

```
0076CC44  55 8BEC          push ebp / mov ebp,esp
0076CC47  85D2 741E        test edx,edx / je exit          ; 记录指针可为 nil
0076CC4B  8B88B0030000     mov ecx,[eax+0x3B0]
0076CC51  3B0A 7514        cmp ecx,[edx] / jne exit        ; dword[rec+0] 必须等于 Self+0x3B0
0076CC55  8A4A08           mov cl,[edx+8]
0076CC58  888854010000     mov [eax+0x154],cl              ; Self+0x154 := byte[rec+8]
0076CC5E  33C9             xor ecx,ecx                     ; Recog = 0
0076CC60  668B5204         mov dx,word [edx+4]             ; **ident = word[rec+4]**
0076CC64  E8EB84FFFF       call 0x765154
```

`0x765154` 拼 0x20 字节正文（`[Self+0x12C]`=X、`[Self+0x130]`=Y、刚写入的 `[Self+0x154]`、
以及 `0x765187` 处 4×`movsd` 从 `[Self+0x168]` 拷来的 16 字节外观块），最后
`0x7651DA call [VMT+0xE0]`。按 REPLICATION_RULES §4.21，`+0xE0` 经
`sub_7651EC → sub_5F7778 → sub_5F6C24` 出网关组播，是**真下发**。

唯一调用者 `0x77BC42`，来自 `0x77BBEC` 的列表回调（`0x77BC0B mov eax,[eax+0x50]` /
`call 0x49EFD4`，回调体 `0x77BC1C`）。**所以这个点的 ident 集合等于那张记录表里
`word[rec+4]` 的取值集合**，静态不可枚举——要么 dump 运行期表，要么找它的加载器。
这是从"不知道是什么"推进到"知道缺哪一件东西"。

### 3.4 B5 —— 顶部滚动 / 居中公告走哪个 ident：**判为原生不存在**

C# `TBaseObject.SysMsg` 在 `MsgType.Notice` 下按首字符三分：`[`→`RM_MOVEMESSAGE`(Recog 0)、
`<`→`RM_SYSMESSAGE`、`{`→`RM_MOVEMESSAGE`(Recog 1，nParam3 带时长)。

两种扫法都是 0 命中：

1. **内联比较**（`b8_notice.py`）：`cmp al,imm8` 与 `cmp byte [reg],imm8` 全镜像扫
   `[`(0x5B) / `<`(0x3C) / `{`(0x7B)，再按"0x200 字节内出现 ≥2 种前缀字符"聚类。
   命中的聚类只有 `0x4B41D0`（RTL 的 JSON/XML 解析）和 `0x5B37xx`（跳表区，反汇编噪声），
   **游戏逻辑段（0x63xxxx–0x79xxxx）一个聚类都没有**。
2. **寄存器传参**（`b9_arrest.py`，防止 1 出假阴性——C# 用的是
   `ArrestStringEx(s,'[',']')` 这种把定界符当参数传的形态）：扫
   `mov al/cl/dl/bl, 括号字符` 共 442 处，按 0x40 字节内 ≥2 种字符聚类，
   成对命中只有 `0x564172`/`0x5B12F2`（都是 VCL），**游戏逻辑段仍然 0**。

叠加上一轮已证的"RM 10099 占跳表槽 99 指向 default `0x6B6241`、原生直接丢弃"，
结论是：**`[` 与 `{` 两种公告样式在本镜像里没有任何原生对应物**。

**本轮不删。** 理由：`SysMsg` 是全局共享入口，删这两支会改动大量 GM 可见行为，
超出 ident 103 的契约范围；而且 0 命中只证明"本镜像没有"，`<` 那一支落到
`RM_SYSMESSAGE` 是活的、也是对的。建议单开一个 `SysMsg` 任务统一裁决。

### 4.2 SM 106 的帧（顺手解出，供后续任务用）

`[obj+0xB99]` 是**禁言标志**（同一个偏移在私聊函数 `0x6C969B` 处触发
`0x6C9758 "已经被禁止聊天。"`）。SM 106 按它二分：

```
006BB1AD  80BF990B000000 cmp byte [edi+0xB99],0
006BB1B4  7433           je 0x6BB1E9            ; 未禁言 -> 广播

; 禁言：只回显给自己
006BB1BB  668B0445803B7D00 mov ax,[eax*2+0x7D3B80]  ; 配色查找表
006BB1C3  50               push eax                  ; Param
006BB1C9  50               push eax                  ; Tag  = byte [ebp-9]
006BB1CA  6A00             push 0                    ; Series = 0
006BB1D7  8BCF             mov ecx,edi               ; Recog = 说话者
006BB1D9  66BA6A00         mov dx,0x6A
006BB1E1  FF9354020000     call [VMT+0x254]          ; 单播

; 未禁言：栈上拼 12 字节头后广播
006BB1E9  66C745D86A00   mov word [ebp-0x28],0x6A    ; Ident  @ +4
006BB1EF  897DD4         mov [ebp-0x2C],edi          ; Recog  @ +0
006BB1FF  668945DA       mov [ebp-0x26],ax           ; Param  @ +6
006BB208  668945DC       mov [ebp-0x24],ax           ; Tag    @ +8
006BB20C  66C745DE0000   mov word [ebp-0x22],0       ; Series @ +0xA
006BB228  E8E7C3F3FF     call 0x5F7614               ; 网关组播
```

即**影子禁言**：被禁言者自己看得见，别人收不到。顺带这段第三次独立确认了
`Recog(4)/Ident(2)/Param(2)/Tag(2)/Series(2)` 的 12 字节头布局。

### 4.3 SM 70 / RM 10612 撞车：**裁定无需处理**，两份证据齐

- **静态零命中**：`RM 10612 = 0x2974` 在全镜像**没有任何立即数装载点**。
  `b6_ident.py 10612` 扫 `mov r16,imm16` 全 8 寄存器 + `mov r32,imm32` 全 8 寄存器，
  结果两段都是空。分发器里那条 `0x6B5D95 → SM 70` 的臂**永远到不了**。
- **计数器零出现**：`srv_AppearTimes.ini` 里**没有 70 这个键**。

所以：
1. **不要"补"SM 70。** 原生自己从不发它，C# 不发才是 FAITHFUL。
2. **不要给 `RM_PHYSICAL_ATT` 改号。** 按 REPLICATION_RULES §1.4，`RM_*` 是进程内队列标签、
   不上线、数值不影响互通；C# 把一个原生死槽拿来接 `SM_PHYSICAL_ATT = 1230`
   （真编号、原生 6 个发出点）是内部自洽且线上正确的。
3. 唯一值得记一笔的：`RM_PHYSICAL_ATT` 与 `RM_NATIVE_UNION_EFFECT` **是同一个值 10612 的两个名字**，
   两个子系统共用一条队列标签、汇到同一个 `SM 1230` 臂。目前自洽，但属于
   §4.18 那类"一个槽两个权威"的隐患，将来任一方要改帧时必须同时看另一方。
