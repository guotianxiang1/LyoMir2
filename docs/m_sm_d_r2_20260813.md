## 1. TFriendRelation 类族（4441/4442/4443/4444/4445）

### 1.1 类身份（VMT 类名，直接读镜像）

Delphi VMT 尾部内联 ShortString 类名：

```
0x6FC92C  0F 'TFriendRelation'        ; 15 字节
0x6FC9A8  12 'TAttentionRelation'     ; 18 字节
0x6FCA28  14 'TNormalBlackRelation'   ; 20 字节
```

三个兄弟类，恰好对应 C# 的 `NativeRelationKind.Friend/Attention/Blacklist`。

### 1.2 单条记录推送（4441/4442/4443）

每类一个虚方法，按 `arg3`（al）选变体，在 `+0x254`（Buf/Len）槽发一条记录：

| ident | VMT 槽 | 入口 fn | 发送点 | Len | 记录布局 |
|---|---|---|---:|---:|---|
| 4441 | `0x6FC928` | `0x6FF3FC` | `0x6FF4D1 66 BA 59 11` `call [ebx+0x254]` | `0x24` | `{name[16], level u16@0x10, job@0x12, guild[15]@0x13, online@0x23}` |
| 4442 | `0x6FC9A4` | `0x6FFD94` | `0x6FFE28 66 BA 5A 11` `call [ebx+0x254]` | `0x16` | `{name[16], level u16@0x10, job@0x12, color@0x13, online@0x14}` |
| 4443 | `0x6FCA24` | `0x700888` | `0x700910 66 BA 5B 11` `call [ebx+0x254]` | `0x14` | `{name[16], level u16@0x10, online@0x12}` |

五元组：`Recog=0, Param=al(操作选择子 0/1/2), Tag=0, Series=0, Len=如上`。
`arg3` 分支（`sub al,1 / jb / je / dec al / jne`）：`0/2` 走完整记录（+0x254），
`1` 走仅名字串（+0x250，`0x6FF505` 等）。名字/公会名取自记录 `[esi+8]`/在线查
（`sub_652784` = `UserEngine.GetPlayObject(name)`，与 C# `GetPlayObject` 同）。

**关键交叉点**：这三种记录 C# **已经逐字节实现**，在
`GameSvr/Services/NativeRelationService.cs:263-283`（`NativeRelationWireCodec.Encode`）：

```
friend    record[16]=level record[18]=job record[19..33]=guild record[35]=online   -> 与 0x24 记录一致
attention record[18]=job record[19]=color record[20]=online                        -> 与 0x16 记录一致
blacklist record[18]=online                                                        -> 与 0x14 记录一致
```

即：**记录编码没有缺口**。4441-4443 的单条推送就是同一编码器 `count=1` 的调用。

### 1.3 登录/登出广播（4444/4445）

`TFriendRelation` 另有两个包装虚方法（VMT `0x6FC914`→`0x700D54` 发 4444，
`0x6FC918`→`0x700D2C` 发 4445）：对主体玩家 `edx`，遍历本对象的 watcher 链表
`[this+0x10]`（TList），逐个用 `UserEngine`（`sub_656C14`→`0x49F98C`）解出仍在线的
watcher，向其推送主体名字 `[player+0x106]`，`Param=this[+4]`。

```
4444  0x6FE921  66 BA 5C 11  mov dx,0x115C  -> call [ebx+0x250]   (先注册: 0x6FE704)
4445  0x6FE85D  66 BA 5D 11  mov dx,0x115D  -> call [ebx+0x250]   (后拆除: 0x6FE6F8->0x6FEEB8)
```

方向（推断，非直证）：4444 包装器先 `sub_6FE704` 把主体的 `[+0x588]/[+0x58C]` 会话键
写入本对象再调两个 VMT（= 注册在场）→ **登录**；4445 包装器先广播再 `sub_6FE6F8`
拆除 → **登出**。srv 计数 4444=928 略 > 4445=900，与"登录多于登出"的采样直觉一致。

### 1.4 为什么 DEFERRED（BLOCKED-D5）

- 触发是 **VMT 派发的对象图**，不是 CM 分发臂。4441 入口 `0x6FF3FC` 全镜像仅 1 个
  dword 引用（VMT 槽 `0x6FC928`），0 个 `E8` 直接调用者；4444/4445 包装器同样 0 个
  `E8` 调用者。`TFriendRelation` 实例也非立即数式 `mov eax,vmt / call Create`
  创建（元类引用），生命周期未在 C# 建模。
- C# `NativeRelationService` 是**按需查 MySQL** 的存储，**没有**"谁把我加为好友"的
  反向 watcher 索引，也没有登录/登出广播钩子。
- 记录编码器在（见 §1.2），但对象模型 + 反向索引 + 触发不在。照原生 1:1 需要移植
  `TFriendRelation` 类族及其在场链表；用"登录时反查 DB 广播"是**另一种实现**，时序/
  顺序不等价，违反 §1.4 逐字节等价，故不做。

**纠正上一轮**：原报告 §4 说"4441 是加好友成功 4433 的附加体"。字节不支持——4441 是
`TFriendRelation` 的 VMT 通知方法，触发是反向广播对象图，**未证实紧跟 4433 之后**。
把它当 4433 的伴随帧去发会捏造触发。

## 2. 4446 —— 元宝寄售状态包（翻案：不是关系包）

发送器 `0x6F75C4` 读玩家 `[player+0x192C]` 子对象：

```
0x6F75CB  8B 83 2C 19 00 00   mov eax,[ebx+0x192C]
0x6F75D3  je  0x6F75F7        ; 为空 -> 报错弹窗(0x79DF74)
0x6F75D5  call 0x712BE4       ; Recog = [+0x192C][+0xC] ? word[[+0xC]+0x26] : 0
0x6F75E7  66 BA 5E 11         mov dx,0x115E  -> call [ebx+0x250]   ; 无 body
```

`[player+0x192C]` 在 `0x6AD9B3 89 87 2C 19 00 00 mov [edi+0x192C],eax`（玩家构造里）
由 `sub_712820` 构造，类 VMT `[0x7121C8]`，**类名 `TYBDealSetInfo`**（元宝寄售挂单）。
`sub_712BE4`：`ecx=[obj+0xC]; if ecx: dx=word[ecx+0x26]`。

CM 触发：relation/gild CM 分发簇的 `0x6DBB3A` 臂（与 CM 4629 组队同一派发器；
具体 CM 号未钉，不臆测）。srv=160。

**纠正上一轮**：原报告 §4 / D6 把 4446 的 `[+0x192C]` 当作未映射的"关系字段"。实为
元宝寄售 `TYBDealSetInfo`。C# 已有 YB 寄售子系统（`NativeYbConsignmentQuery`、
`NativeYbDealPurchaseStateMachine`），但后者 host-driven 且 dormant，`[+0x192C]` 这个
挂单集合子对象未建模。故 4446 仍 DEFERRED（BLOCKED-D6），但归属已澄清。
