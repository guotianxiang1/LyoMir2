## 2. 【核心】目标优先重扫：找回 8 个被漏掉的原生 ident

### 2.1 扫描口径

严格按 REPLICATION_RULES §4.20 做「从发送槽反查」，不按 `mov dx,imm16` 形状正查：

1. 全 CODE 段枚举 `FF /2 disp32` 且 `disp32 ∈ {0x250,0x254,0xE0,0xD8}` 的间接调用
   —— **1031 处**（`0x250`=554、`0x254`=182、`0xE0`=214、`0xD8`=81），其中主槽
   `[+0x250]/[+0x254]` **736 处**（`c3_targetfirst.py`）。
2. 每个调用点回溯到 `55 8B EC` 函数首（找不到就退化成 0x40..0x200 的窗口）。
3. 小解释器反解 `edx`。**关键改进：解释器同时跟踪 `[ebp±N]` 栈槽**
   （`c8_memresolve.py` 的 `class M`），并枚举「直落 + 每条前向跳转 + 两两组合」
   的路径，补齐 if/else 合流臂。
4. ident 来自寄存器/栈参的函数升级为 WRAPPER，枚举其 `E8` 调用者递归解
   （`c9_wrappers.py`，10 个包装器；`0x707014 → 0x7059D0` 的二级包装再追一层）。

**只跟踪寄存器时**：736 个主槽点解出 702 imm / 31 未解，产出 477 个 ident，
与 507 全集的差集**为空**（看起来「完全一致」）。
**加上栈槽跟踪后**：解出 713 imm，产出 **487** 个 ident，其中 **12 个不在 507 全集里**。

这就是 §4.20 说的那个坑的精确形态：**ident 不是装进寄存器再发，而是先写进
`[ebp-N]` 局部、绕一段代码后再 `mov dx,[ebp-N]`**，寄存器级解释器整条吞掉。

## 3. 复核中查出的前人结论错误

### 3.1 【重要】14 个「有生产流量但不在全集」的 40xx 不是 M2Server 的 SM

第 1 轮 B6 把 `4332`（48 次）挂起，怀疑扫描器不完备。用计数器对全片重扫，
落在 `[1257,4414]` 且有 `srv` 流量却不在全集的共 **14 个**：
`4003(38828) 4004(37539) 4010(81794) 4012(12797) 4013(740) 4014(64) 4017(51946)
4018(5359) 4031(1) 4039(9007) 4040(960) 4041(37019) 4042(233) 4332(48)`。

**结论：它们不是 M2Server 发的，是同一条网关上跑的手游登录/选服/选角链路。**
三条证据：

1. **全 CODE 段 0 个立即数装载**（20 种装载形态 + 裸 16 位回溯，
   `c2_imm40xx.py` / `c2b_control.py`）。同一脚本的阳性对照全部命中：
   `4230`=2、`3555`=2、`2831`=5、`3322`=2、`4412`=4、`4414`=1、`1264`=13。
   裸 16 位串在 CODE 里确实有命中（`4017` 352 处、`4040` 139 处），但逐个回溯
   **没有一处是立即数操作数**，全是别的指令的字节巧合。
2. **发送方在 DBServer**：`4039` = `CM/SM_SELCHR_EXIT`，由
   `DBSvr/Services/UserSocService.cs:669` 处理，注释引的原生是
   `0x5CE317 cmp word [eax+4],0xFC7`；`4332` 是排队位次通知，
   `DBSvr/DBShare.cs:306` 引 `call 0x5CFCAC`、`opcode 0x10EC`。
3. **GameGate 自己也这么归类**：`GameGate-CS/Core/GateServer.cs:708-710`
   把 `4012-4017 / 4004 / 4002 / 100-107 / 4041 / 4039 / 4031` 列为
   「角色管理/登录命令」单独放行。

所以 **B6 的 4332 部分可以关闭**：不是扫描器漏了，是它根本不由 M2Server 产生。
（B6 里 `34 = 18,255,061` 那半条是真漏，本轮已在 §2.2 独立复现，属 A 片。）

`MakeDefaultMsg(2885, player.ObjectId, 0, 0, userMagic.MagicInfo.wMagicID)`
—— **魔法 id 发在 Series，Param 留 0**，客户端读合击技进度整体错一格。
20 字节 body 本来就对，未动。

### 4.2 `SM 2821` 安全区帧五元组全错位 + 自造 ASCII 载荷 —— 提交 `aaa7a21a`

这条是任务点名的「隐蔽形态：C# 用自造 ASCII 文本包顶替原生」的变体——
ident 是真的，**载荷是编出来的**。

原生（`sub_6B2D38`，与 C# 同在 1000 ms tick 里）：

```
006B308B  8B 45 FC / E8 C1 53 0B 00  call 0x768454        ; InSafeArea
006B3096  3A 82 FE 03 00 00          cmp al, [edx+0x3FE]  ; m_boInSafeArea
006B309C  74 43                      je  0x6B30E1         ; 没变化 -> 不发包
006B30A3  88 91 FE 03 00 00          mov [ecx+0x3FE], dl
006B30A9  84 D2 / 74 1B              test dl,dl / je 0x6B30C8
006B30AD  6A 06 6A 01 6A 00 6A 00 33 C9 66 BA 05 0B   ; Param=6 Tag=1 Series=0 Recog=0
006B30C8  6A 06 6A 00 6A 00 6A 00 33 C9 66 BA 05 0B   ; Param=6 Tag=0 Series=0 Recog=0
006B30C0 / 006B30DB  FF 93 50 02 00 00  call [ebx+0x250]
```

`0x768454` 就是 `InSafeArea`：`call 0x772EB8` 为真直接 TRUE，否则查
`byte [envir+0x84]`，再用 `CurrX=[ebx+0x12C] / CurrY=[ebx+0x130]` 调 `0x7684DC`。
`[obj+0x3FE]` 全 CODE 段只有三处访问（`0x6B3096` 读比较、`0x6B30A3` 写、
`0x6B3206` 读），是这个标志的唯一权威。

C# `TPlayObject.Message.cs:396`（改前）：

```
SendDefMessage(Grobal2.SM_COMMON_INFORMATION,
    boInSafeArea ? 1 : 0, m_nCurrX, m_nCurrY, 0,
    boInSafeArea ? "safe_enter" : "safe_exit");
```

即 `Recog=1|0, Param=CurrX, Tag=CurrY, Series=0, sMsg="safe_enter"|"safe_exit"`——
**五个字段没有一个对**。`"safe_enter"` / `"safe_exit"` 在 16.8 MB 全镜像里
**ASCII 0 命中、大小写不敏感 ASCII 0 命中、UTF-16LE 0 命中**。
ident 2821 本身线上 **247,034 次**，所以只改帧形不动 ident。

改后：`SendDefMessage(SM_COMMON_INFORMATION, 0, 6, boInSafeArea ? 1 : 0, 0, string.Empty)`。

**同一处还有两条控制流分歧，本轮只登记不改（不在 SM 帧的职责内，且会与
Run 的属主代理撞车）**：

1. **原生这段没有行会战门。** `0x6B308B` 直接跟在
   `0x6B3054 cmp edx,0x75300 / jbe 0x6B308B` 之后，无任何 `m_MyGuild` 判断；
   C# 外面套了 `if (m_MyGuild != null && m_MyGuild.GuildWarList.Count > 0)`。
   后果：**无行会的玩家在 C# 里 `m_boInSafeArea` 永远不更新**，2821 也永远不发。
2. **原生这段没有 `RefNameColor()`。** C# 在转换处调了它。
3. **反过来 C# 缺一道门**：`0x6B3206 cmp byte [edx+0x3FE], 0 / 0x6B320D jne 0x6B32A1`
   把「挤人」逻辑整段挡在安全区外，其后正是
   `cmp eax,3 / jl / cmp ebx,0xBB8 / ja / cmp eax,2 / jne / cmp ebx,0x2710 / jbe /
   cmp ebx,0x4E20 / jae` —— 与 C# `Message.cs:359-363` 的
   `tObjCount>=3 && >3000 || tObjCount==2 && >10000` 且 `<20000` → `CharPushed` 一一对应，
   **而 C# 没有那道安全区门**。玩家可见后果：安全区里也会被挤位。

### 5.2 活 ident 上缺的子行为：组队申请超时清扫（SM 4412，线上 3,270 次）

C# 的 4412 有三个下发点，与原生三处逐字段对得上：

| 原生 | 帧 | C# |
|---|---|---|
| `0x6F3AB0`（`sub_6F39B4` 排入申请） | Recog=1, Param=type | `NativeGroupProtocol.cs:90` |

第四处的证据：

```
006C3AE3  8B 86 78 0A 00 00  mov eax,[esi+0xA78]      ; 待处理申请 TList

006C3B06  E8 35 48 D4 FF     call 0x408340            ; GetTickCount
006C3B0C  2B C2              sub eax, edx
006C3B0E  3D 10 27 00 00     cmp eax, 0x2710          ; 10,000 ms
006C3B13  0F 86 4C 01 00 00  jbe 0x6C3C65             ; 未超时 -> 跳过
006C3B42  0F B6 40 04        movzx eax, byte [entry+4]
006C3B46  50                 push eax                 ; Param  = 申请类型
006C3B47  6A 00 / 6A 00      ; Tag = Series = 0
006C3B51  81 C2 06 01 00 00  add edx, 0x106           ; 申请人名（ShortString）
006C3B5F  50                 push eax                 ; sMsg

006C3B6A  FF 97 50 02 00 00  call [edi+0x250]
```

由 Run 每 tick 调用（`0x6B3CC5 call 0x6C3ABC`）。记录布局

这是功能层补齐（要加时间戳字段 + Run 钩子），**登记，交主控排期**。
