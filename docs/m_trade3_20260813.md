## 2. 成交原子性

### 2.1 原生真实序（`sub_6C4580`）

```
阶段 A 前置 6 门         0x6C45A2..0x6C45E9   任一不过 → 静默返回（不发包、不改状态）
阶段 B m_boDealOK := 1   0x6C45EF             ← 注意：6 门之后才置位
阶段 B' 双侧 tick 门     0x6C4603             不过 → DealCancel
阶段 C 对端已确认?       0x6C4643             否 → 0x6C49C1 两条提示，**不取消**，返回
阶段 C' 权限门 ×2        0x6C4650 / 0x6C4693  不过且有押金 → 脚本 + DealCancel
阶段 D 四道容量检查      0x6C46E4 / 0x6C4705 / 0x6C4720 / 0x6C473F
                          任一失败 → 全部 jmp 0x6C49B8 → DealCancel（fail-fast，无 per-check 消息）
阶段 E 计数器            0x6C4758  inc dword [0x7D3A90]
阶段 F 我方物品 → 对端   0x6C475E..0x6C482F   i = 0..n-1 升序，[对端 vmt+0x248]，**返回值丢弃**
阶段 G 我方金币 → 对端   0x6C4835..0x6C487E   >0 才走，[对端 vmt+0x28C] = IncGold，**返回值丢弃**
阶段 H 对端物品 → 我方   0x6C488A..0x6C4953   同 F
阶段 I 对端金币 → 我方   0x6C4959..0x6C49A4   同 G
阶段 J 清理（对端先）    0x6C49A4 / 0x6C49AF  各调 sub_6C4A98
```

### 2.2 回滚：**原生没有回滚，一步都没有**

F/G/H/I 四步的返回值全部丢弃（`call [vmt+0x248]` 之后紧接 `mov eax,esi` 去做日志，
没有 `test al,al`）。**阶段 D 的四道前置检查是唯一的保护**。这是可以成立的，因为：

- 押金物品在**放物**阶段就已经 `m_ItemList.Delete(i)`（`0x6C427F`）离开背包，
  成交时只做「进」不做「出」，两侧的容量在 D 与 F/H 之间不会被第三方改变；
- 押金金币在**改押金**阶段就已从 `m_nGold` 扣走（`0x6C44D4`），同理；
- 因此 D 检查的量与 F/G/H/I 实际搬运的量恒等。

**结论：C# 与原生同构，没有引入回滚，也不应引入。** 审计工具钉住了
「四道容量检查必须全部排在第一次物品交割之前」这条不变式——一旦有人把某道检查
挪到交割之后，那才会变成真的吞物。

### 2.3 背包满 / 负重在哪一步查

- **背包满**：阶段 D，`[vmt+0x244]` = `sub_6D0AE8`：
  `mov eax,[eax+0x508] / mov eax,[eax+8] / and edx,0xFF / add eax,edx /
   cmp eax,0x30 / setle al` —— 即 `Count + n <= 48`，**48 是硬编码立即数**，
  且入参被 `and edx,0xFF` 截成字节（调用点也确实是 `mov dl,byte [eax+8]`；
  押金上限 12，截断不可达）。
  C# 用 `BagCapacity.Of(this)`，无插件时回落 `NativeSlots = 48`，形状
  `cap - count < n → 拒绝` 与 `count + n <= cap` 等价。FAITHFUL。
- **金币上限**：阶段 D，`sub_6D7948`：`test edx,edx / jl → TRUE(拒绝)` ；
  `add edx,[eax+0x15C] / cmp edx,[eax+0x68C] / jg → TRUE(拒绝)`；否则 FALSE。
  C# `m_nGoldMax - m_nGold < deal` 等价于 `gold + deal > max`。FAITHFUL。
  （**残留**：原生对 `deal < 0` 也拒绝，C# 不拒绝。当前不可达——`ClientChangeDealGold`
  的 `jle` 门保证 `m_nDealGolds > 0`。记录，未改。）
- **负重**：交易链路**全程不查负重**。原生只在**取仓**查
  （`0x6C2EBD call 0x73C950 / je 0x6C2FBC → esi = -1`）。这是原生行为，不要「补」。

## 3. 金币上限：全仓 `m_nGold` 越权点清单

先纠正一条前提：**「交易里的裸 `+=` 一定是绕过上限」这个判断对本镜像不成立。**
交易链路有两处裸写，两处都是原生原样：

| C# | 原生 | 判定 |
|---|---|---|
| `TPlayObject.cs` `GetBackDealItems` `m_nGold += m_nDealGolds` | `0x6C4161 01 83 5C 01 00 00 add [ebx+0x15C],eax` | **FAITHFUL，勿改** |
| `Operate.cs` `ClientChangeDealGold` `m_nGold = m_nGold + m_nDealGolds - nGold` | `0x6C44D4 89 83 5C 01 00 00 mov [ebx+0x15C],eax` | **FAITHFUL，勿改** |

两处安全的理由相同：动的是**本人押金**，押金进出是同一个裸写的逆运算，回加不可能
超过扣走前的值。改成 `IncGold` 反而会因 `0x6D7924 jle`（≤0 拒绝）在零押金时返回
false，并在拒绝时**静默吞掉押金**——那才是刷/吞。

真正走上限门的是成交交割：`0x6C4847` / `0x6C496D` 的 `call [ecx+0x28C]`，
`[0x6AC8C8+0x28C] = 0x6D791C = IncGold`（`vmt.py` 实测）。C# 两处都用 `IncGold`，FAITHFUL。

## 4. 绑定物 / 不可交易物

判定点唯一：`0x6C4230 E8 67 F6 0B 00 call 0x78389C`，`edx = 2`（mode 2 = 交易）。
`sub_78389C` 前置阶（绑定字 != 0、`Reserved02 & 0x0800`、`& 0x4000`）返回 **1**；
mode 2 阶（`[item+0xFC] != 0` 或 `Reserved02 & 0x0200`）返回 **3**；放行返回 0。
C# `NativeItemDropDestroy.CheckTransferPermission` 形状一致（`[item+0xFC]` 无对应
字段，已就地记录为缺口，不是本轮引入）。

已修：**TRADE-60** 失败回包 Recog 现在带这个码（原生 `0x6C42A2 mov ecx,[ebp-0x10]`）。

### 4.1 TRADE-61 —— MISSING，**已定位但未落地，需主控授权**

原生在跑不可交易判定之前有一道 **GM 旁路**：

```
0x6C41AD  80 BB 75 06 00 00 04   cmp byte [ebx+0x675], 4      ; 自己权限
0x6C41B4  73 13                  jae 0x6C41C9                 ; >= 4 → al := 1
0x6C41B6  8B 83 AC 0B 00 00      mov eax,[ebx+0xBAC]
0x6C41BC  80 B8 75 06 00 00 04   cmp byte [eax+0x675], 4      ; **对端**权限
0x6C41C3  73 04                  jae 0x6C41C9                 ; >= 4 → al := 1
0x6C41C5  33 C0 / EB 02          xor eax,eax
0x6C41C9  B0 01                  mov al, 1
0x6C41CB  88 45 EE               mov [ebp-0x12], al
   ...
0x6C421D  80 7D EE 00            cmp byte [ebp-0x12], 0
0x6C4221  75 1B                  jne 0x6C423E                 ; 旁路成立 → **整段跳过** 0x78389C
```

即：**只要交易双方任一方权限 >= 4，绑定物 / 禁交易物就可以直接放进交易格。**
C# 完全没有这一段。

**我没有落地，理由**：这是在整个车道里唯一一道拦绑定物的门上开口子，而且开口
条件挂在**对端**权限上（不是自己），一旦 `m_btPermission` 的来源在 C# 侧有任何
偏差，就是全服绑定物解绑。按「不确定一律 fail-closed，宁可少改」，交给主控裁决。
落地时必须同时确认 `m_btPermission` 与原生 `[obj+0x675]` 的取值域一致
（同一字节在 `AddItemToBag` 的 `<= MaxStampedGmLevel` 里也被用作 GM 判据）。

### 4.2 TRADE-62 —— DIVERGENT，未落地

原生门序：`不可交易判定`(0x6C4230) → `名字比较`(0x6C424B) → `12 格上限`(0x6C425A)。
C# 门序：`名字比较` → `12 格上限` → `不可交易判定`。

后果只在「id 命中但名字不匹配、且该物品不可交易」时可见：原生发非零码，C# 继续
循环并最终发 0。名字由客户端提供，不匹配本身就是异常包，影响面极小。**未改**——
调整循环结构的风险大于它修的东西。

（0/1/2）压进了 FULL 与 FAIL 两个回包，C# 两处都发全 0。这与上轮 TRADE-45 的失败码
回填是同一族问题。**BLOCKED**：要落地必须先钉死 `[vmt+0x250]`(`sub_6D7CB0`) 的
四个压栈参数与 C# `SendDefMessage(wIdent, nRecog, nParam, nTag, nSeries)` 的对位，
猜不得。建议与 TRADE-45 合并成一个「仓库回包字段」专项。

**存疑（未改）**：C# 存仓成功路径调 `M2Share.UserEngine.SaveHumanRcd(this)`，
而原生 `0x6C2BF5..0x6C2CC8` 这一段里没有存盘调用。可能是别处触发，也可能是
臆造。证据不足，只记录，不动——多存一次盘不丢物。

## 6. 摆摊

C# 的摆摊是前人一整套 `NativeStall*`（12 个文件），且整体由
`NativeStallWriteGate` 门控为 DORMANT。本轮只做**独立复核**，未改：

- **事件类型 0x29 = 41 属实，我自己反出来的**：`sub_61A36C`
  `0x61A396 6A 29 push 0x29`，前面 `0x61A383 mov ebx,0x7B464C` 取事件表基址，
  `0x61A3A0 call 0x779190` 按坐标+类型查事件，命中则 `0x61A3A9 call 0x7199CC` 关闭。
- **`sub_61A36C` 恒返回 1 属实**：`0x61A3B4 B8 01 00 00 00 mov eax,1` 是唯一出口，
  与查找结果无关。C# 注释里 "ALWAYS returns 1" 的说法成立。
- 顺带订正一处注释细节：`0x61A37E mov esi,1` 使那个 `add ebx,8 / dec esi / jne`
  的循环**只跑一次**，所以 `unk_7B464C` 在这里是一对 (x,y) 基址而不是被遍历的数组。
- 买家扣款 `m_nGold += (int)outcome.BuyerGoldDelta`（负值）是减不是加，不涉上限门；
  卖家收款走结算邮件而不是直接加钱，故摆摊链路上**没有**绕过 `IncGold` 的加钱点。

上架 / 下架 / 购买 / 摊主下线四条链路的逐字节对账**不在本轮完成**（前人已有
`NativeStallBuyConservationCheck` / `StallNoOpDispatchCheck` 钉住守恒与空分发）。
本轮只把用户给的 `0x29` 这条线索验成了硬证据。

## 8. 我在复核中发现的前人 / 既有结论错误

1. **`ClientDealEnd` 注释把 `[obj+0x73]` 写成 `m_boDeath`，代码也照错的写了**——
   正是 REPLICATION_RULES §4.6 点名的那一类。本轮独立复跑写点计数：
   `C6 43 73 01` **1 命中** @`0x7680EF`，`C6 43 74 01` **5 命中**含 `0x766323`。
   已修（`57c35d40`）。

2. **「交易里的裸 `m_nGold +=` 都是绕过上限」是错的**（§3）。`0x6C4161` 与
   `0x6C44D4` 两处原生就是裸写，改成 `IncGold` 会引入吞押金的新缺陷。
   本轮把这两条写进了审计工具的**反向断言**（断言它们**不得**变成 `IncGold`），
   免得下一个代理「顺手修好」。

3. **`GetBackDealItems` 的本体是 `sub_6C4114` 不是 `0x6C40B8`**。上轮报告写
   「`GetBackDealItems`（原生 `0x6C40B8`）」——`0x6C40B8` 是 `OpenDealDlg` 尾部
   对它的 `call`，不是函数起点。差 0x5C，正好差掉了倒序循环那一段。

4. **`sub_6C4580` 的容量检查不是「C# 自己算」，原生走的是虚槽**：
   `[vmt+0x244] = 0x6D0AE8`（背包）、`0x6D7948`（金币）。前者的容量是**硬编码
   `cmp eax,0x30`**，后者读**每角色** `[eax+0x68C]`。两者来源不同，不要统一成配置。

5. **「受伤会取消交易」对本镜像是假的**。`0x6C43C4` 的 11 个调用点里没有
   `StruckDamage`（`sub_73F9FC` / `sub_767A18`）。这条上轮工具注释里已写对，
   本轮用 `xref.py` 独立复核确认。

6. **`ClientAddDealItem` / `ClientDelDealItem` 原生都没有 `m_boDealing` 门**，
   只有 `m_DealCreat != nil`。C# 两处都多加了 `!m_boDealing`。这是收紧、不丢物，
   本轮**未动**（去掉它是放宽，应单独授权）。记录在案，免得被当成 FAITHFUL 抄走。
