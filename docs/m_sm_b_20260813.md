## 2. 解码基准

### 2.1 发送槽签名（沿用并复验）

```
[obj+0x250]  SendDefMessage(Self=eax, wIdent=dx, nRecog=ecx, Param, Tag, Series, sMsg)
[obj+0x254]  同上，末两个栈参换成 (Buf, Len)
[obj+0x0E0]  虚发送器，尾部多一个 boFlag
栈参从左到右：#1=Param #2=Tag #3=Series #4=sMsg|Buf #5=Len #6=boFlag
```

### 2.2 帧解码器必须按槽的实参个数对齐

向后收集 push 块会一直走到上一条 `call`/分支，因而**把函数序言的 `push ebx/esi` 一起吞进来**。
`SM 888` 是这个坑的样本：收到 6 个 push，若按前 4 个读会得到
`Param=ebx, Tag=esi, Series=0x3E7`，与 C# 完全对不上；按槽实参个数（`0x250`=4、`0x254`=5、`0xE0`=6）
取**末尾 N 个**才得到真实的 `Param=0x3E7, Tag=0, Series=0`，与 C# 一致。
`b7_frames.py` 会把丢弃的序言 push 单独打出来（`dropped-prologue-pushes:`）以便复核。

### 2.3 RM 入队链（本轮新反出来，§4.1 靠它定案）

```
sub_765E68(eax=收件人, edx=主体actor, cx=tag, [ebp+0x10]=nParam3,
           [ebp+0x14]=nParam2, [ebp+0x18]=nParam1, [ebp+0x1C]=wParam)
  00765E96  66 89 03      mov word[rec+0x00],ax   <- tag
  00765E9D  66 89 43 02   mov word[rec+0x02],ax   <- wParam
  00765EA4  89 43 04      mov [rec+0x04],eax      <- nParam1
  00765EAA  89 43 08      mov [rec+0x08],eax      <- nParam2
  00765EB0  89 43 0C      mov [rec+0x0C],eax      <- nParam3
  00765EB6  89 43 24      mov [rec+0x24],eax      <- BaseObject
```

`[VMT+0xD8] = 0x0076533C` 是**入队式组播**，把自己的 `cx` 原样转成 `765E68` 的 wParam：

```
0076533C  66 89 4D FA   mov word[ebp-6],cx        ; 收下调用方的 cx
00765501  66 8B 45 FA   mov ax,[ebp-6] / 50 push  ; -> 765E68 的 [ebp+0x1C] = wParam
00765522  E8 41 09 00 00 call 0x00765E68
```

### 4.1 `SM 801` / `SM 807` —— Series 多打了光照高字节（已修，合计 1,075,002 次）

第 1 片把「移动/受击族 Series 是否含光照」列为 BLOCKED **B3**，因为缺入队侧证据。
本轮把这两个 ident 的入队侧完整反出来，**结论是不含光照**。

接收臂（`RM 10331`，`0x6B59E6`）原样取 wParam：

```
006B59E6  66 8B 43 04       mov ax,word[ebx+4] / 50 push   ; #1 Param  = LoWord(nParam1)
006B59EB  66 8B 43 08       mov ax,word[ebx+8] / 50 push   ; #2 Tag    = LoWord(nParam2)
006B59F0  66 8B 43 02       mov ax,word[ebx+2] / 50 push   ; #3 Series = wParam（原样）
006B59F5  8B 53 24          mov edx,[ebx+0x24]             ; 主体 actor
006B59F8  66 B9 21 03       mov cx,0x321
006B59FF  E8 50 74 00 00    call 0x006BCE54
```

`RM 10331 / 10336` 在**全镜像只有一个生产者**（`ba_enq.py` 对 `0x285B`/`0x2860`
枚举 3 种 16 位 + 8 种 32 位装载形态，各只命中 1 处），而且它本身又是一条分支合流臂：

```
00768ECA  83 7D 0C 01       cmp dword[ebp+0xC],1
00768ECE  75 06             jne 0x00768ED6
00768ED0  66 B8 60 28       mov ax,0x2860        ; RM 10336 -> SM 807
00768ED4  EB 04             jmp 0x00768EDA
00768ED6  66 B8 5B 28       mov ax,0x285B        ; RM 10331 -> SM 801
00768EDA  8B 93 2C 01 00 00 mov edx,[ebx+0x12C] / 52 push   ; CurrX
00768EE1  8B 93 30 01 00 00 mov edx,[ebx+0x130] / 52 push   ; CurrY
00768EE8  6A 00 6A 00 6A 00 push 0 x3
00768EEE  33 C9             xor ecx,ecx
00768EF0  8A 8B 54 01 00 00 mov cl,[ebx+0x154]   ; <- wParam 源 = 方向字节，零扩展
00768EF6  8B D0             mov edx,eax          ; wIdent = RM tag
00768EFC  FF 96 D8 00 00 00 call [esi+0xD8]      ; = 0x0076533C
```

`xor ecx,ecx / mov cl,…` 保证**高 8 位恒为 0**；`0x76533C` 经 §2.3 的链路把它原样写进
`word[rec+2]`。所以线上的 Series 高字节一定是 0。

C# 生产侧 `TBaseObject.cs:2190/2195 SendRefMsg(RM_SPACEMOVE_SHOW2/SHOW, m_btDirection, …)`

`HUtil32.MakeWord(ProcessMsg.wParam, BaseObject.m_nLight)`。已改回 `ProcessMsg.wParam`。

> 这条只结清了 801/807。第 1 片 B3 里的移动/受击族（RM 10001/10002/10003/10004…，
> 合计 6 亿次）走的是**别的生产者**，仍未取证；但本节给出了可照抄的取证路径：

### 4.2 `SM 708 (SM_MYSTATUS)` —— 饥饿值被塞进 Param（已修，551,868 次）

原生 ident 708 **只有一个下发点**，在 `sub_6B6BEC`：

```
006B6BF4  33 F6                 xor esi,esi
006B6C02  83 CE 01              or  esi,1        ; Envir[+0x5D]
006B6C0B  83 CE 02              or  esi,2        ; Envir[+0x5C]
006B6C4E  83 CE 08              or  esi,8
006B6C7E  83 CE 20              or  esi,0x20
006B6C81  6A 00 x4                               ; Param = Tag = Series = 0
006B6C89  8B CE                 mov ecx,esi      ; nRecog = 区域状态位掩码
006B6C8B  66 BA C4 02           mov dx,0x2C4
006B6C93  FF 96 50 02 00 00     call [esi+0x250]
```

`sub_6B6BEC` 有 3 个调用者：`0x6B6B91`（FreePK 区标志 setter，
`3A 9E C4 04 00 00 cmp bl,[esi+0x4C4]` 变化才发）、`0x6B954D`（登录）、
`0x6B96C2`（换地图，紧接在 `66 BA 7A 02 mov dx,0x27A` = SM_CHANGEMAP 之后）。

**流量算术独立佐证原生没有饥饿驱动的 708**：

```
SM_CHANGEMAP(634) = 500,885
SM_LOGON(50)      =  50,911
合计              = 551,796
实测 708          = 551,868      差 72 = FreePK 标志变更路径
```

C# `RefUserState()`（`TPlayObject.cs:716`）是 `sub_6B6BEC` 的对应物，帧是对的。
但 `case Grobal2.RM_MYSTATUS:` 另发了一帧 `Recog=0, Param=GetMyStatus()`，
而 `GetMyStatus()` 是**饥饿度**（`m_nHungerStatus / 1000`，钳到 4）。
客户端把这个字段当区域位读，于是饥饿=1 被读成「战斗区」、2 读成「安全区」、
3 读成两者、4 读成「自由 PK 区」—— 是一个会让 PK 区指示器随饥饿闪烁的活 bug。
已把该 case 改为调用 `RefUserState()`，使 C# 所有 708 下发都用原生帧。

**剩余差异（登记，不改）**：C# 还会在饥饿档位变化（`TPlayObject.cs:2690`、
`Message.cs:672`）和 `YanshenApi.Rename`（`YanshenApi.cs:2948`）时触发 708，
原生没有这两个触发点。这是触发次数问题，不是帧布局问题，交饥饿子系统负责人。
