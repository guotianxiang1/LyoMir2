## 1. 先把「四道门只有 6 道」这件事自己复核一遍

上一轮的结论正确，我独立复核确认。`sub_6C3F00` 全函数 `0x6C3F00..0x6C4055`
（含 SEH 序言与 Delphi 收尾）的**全部**条件分支：

```
0x6C3F1C  80 BB 61 04 00 00 00  cmp byte [ebx+0x461], 0   / 0F 85 jne 0x6C402D   自己在交易 → 静默返回
0x6C3F32  85 F6                 test esi, esi             / 0F 84 je  0x6C4015   前方无对象 → SM 0x2A2
0x6C3F3A  3B DE                 cmp ebx, esi              / 0F 84 je  0x6C4015   前方是自己 → SM 0x2A2
0x6C3F49  3B D8                 cmp ebx, eax              / 0F 85 jne 0x6C3FFB   对端前方非我 → SM 0x2A2
0x6C3F51  80 BE 61 04 00 00 00  cmp byte [esi+0x461], 0   / 0F 85 jne 0x6C3FFB   对端在交易
0x6C3F5E  80 BE 78 01 00 00 00  cmp byte [esi+0x178], 0   / 0F 85 jne 0x6C3FFB   对端非玩家
0x6C3F6B  80 BE A0 0B 00 00 00  cmp byte [esi+0xBA0], 0   / 74 je  0x6C3FE6      对端 m_boAllowDeal
```

其余指令只有两次字符串拼接（`0x405774`/`0x40581C`）、两次 `[vmt+0xD4]` 发提示、
一次 `[vmt+0x250]` 发 SM 0x2A2、两次 `call 0x6C4090`（OpenDealDlg）。
**没有 GetTickCount、没有全局开关、没有第二个布尔位。**

分派桩也没有前置：`0x6D913E 8B 45 FC mov eax,[ebp-4]` / `E8 BD AD EE FF call 0x6C3F00`。

### 1.1 一条方法论订正：配置键名扫描在本镜像**无效**，不能拿来判 INVENTED

我先按常规做了 ASCII 大小写不敏感的配置键扫描，结果
`DisableDeal` / `TryDealTime` / `LockDealAction` 全 0 命中 —— 看着像铁证。
但**对照组同样全 0**：`ClickNpcTime` 0、`DealOKTime` 0、`SaveHumanRcdTime` 0、
`TryModeUseStorage` 0、`GoldMax` 0。而这些配置在 C# 里都有原生对应实现且已判 FAITHFUL。

结论：**战神 M2Server 不把配置键名以明文字符串存放在镜像里**，
所以「配置键 0 命中」在本镜像上不构成任何证据。后续代理不要用这条推理。

**有效的是 GBK 中文消息串扫描**，对照组可证：

| 串 | 命中 |
|---|---|
| 对方拒绝和你交易 | 1 @ `0x6C407C`（len=18） |
| 和你开始交易了 | 1 @ `0x6C4061`（len=17） |
| 交易取消 | 1 @ `0x6C4448` |
| 普通仓库 / 账号仓库 / 药品仓库 | 各命中 @ `0x6C2D48` / `0x6C2D5C` / `0x6C3064` |
| 暂时关闭 | 14（证明该词组本身可索引） |

在这个能工作的扫描器下，下列串 **GBK + 裸 ASCII + UTF-16LE 三编码全 0**：
`交易功能`、`稍候再交易`、`再交易`、`无法进行此操`、`此操作`、
`密码保护系统`、`仓库已被加锁`、`开锁密码`、`输入正确的密码`、`对方禁止进入交易`。

## 2. 四道门逐条裁决

四道门在 `TPlayObject.Operate.cs`（改动前 1561 / 1570 / 1575 / 1587 行）。
上一轮不敢删的三条理由我逐条查了，结论是**三条里两条不成立、一条成立**。

### 门 A1 — `M2Share.g_Config.boDisableDeal` → **删除**（提交 `e15e37dc`）

上一轮的理由是「与眼神 `IsTradeBanned()` 同处一个条件，删了会连累插件功能」。
这个理由针对的是**复合表达式**，不是这一半本身 —— 拆开就没有了。

判 INVENTED 的证据：原生无此门（§1）；消息「交易功能」0 命中（对照组有效）。

判**死开关**的证据（这一条决定它能零风险删）：

- 全仓库对 `boDisableDeal` 的赋值只有一处：`GameSvrConfig.cs:1244 boDisableDeal = false;`
- `GameSvrConfig.cs` 内 `ReadBool` / `ReadInteger` / `ReadString` 命中数 **0** —— 没有 ini 读取器
- `M2Share.cs:1695` `g_Config = new GameSvrConfig();` 直接构造

即**没有任何途径把它置 true**，删除的运行期差量可证为 0。
这是四道门里唯一一条「既是 INVENTED、又能证明删了什么都不会变」的。

配置字段本身留在 `GameSvrConfig`（不动 Configs 层，避免夹带），现已无消费者。

### 门 A2 — 眼神 `IsTradeBanned()` → **保留**，标注为插件扩展（提交 `e15e37dc`）

`YanshenApi.cs:3702-3706`：`Enabled("禁止交易地图") && 地图名长度 == 15`。
这是 2.0.x 的地图名长度 15 惯用法，与 `IsPetRestBlocked` 同形。

- 它**不是 M2 原生门**，但也**不是本移植自造**——是本项目明确要复刻的插件扩展。
- `ClientDealTry` 是它在全仓库**唯一的活消费点**。删掉它，按 §3「死代码算 MISSING」
  该 API 立刻变成 MISSING，等于在一条 TRADE 提交里废掉插件功能，正是 §4.3 点名的夹带。
- 消息沿用 `g_sDisableDealItemsMsg`：插件自身文案落在 Themida 逐函数虚拟化段
  （§5.1.0.3），不可取证，换文案是新的臆造。

`AuditTools/YanshenApiAccessCheck/Program.cs:126-130` 钉的是 `IsTradeBanned()` 的返回值，
不钉调用点，所以删调用点不会让工具变红 —— 这恰恰是「工具不红 ≠ 没坏东西」的例子。

### 门 B — `dwTryDealTime` 三秒节流 → **删除，独立提交**（提交 `92d57c4b`）

上一轮的理由是「`dwTryDealTime` 与 `m_boCanDeal` 是配置化功能」。
「配置化」这半不成立：和 `boDisableDeal` 一样没有读取器，`dwTryDealTime = 3000`
（`GameSvrConfig.cs:1241`）是编译期常量，运营改不了。

但它与 A1 有本质区别：**它是活的**。`m_DealLastTick` 在 `DealCancel`
（`TPlayObject.cs:1290`）与 `OpenDealDlg`（`TPlayObject.cs:2946`）都会刷新，
所以取消一次交易后 3 秒内再发起会被拦下并收到非原版提示「请稍候再交易!!!」。
这是玩家可见的真实偏离。

证据：`sub_6C3F00` 全函数 tick 引用数为 0（call 目标只有 `0x767E80` / `0x405774` /
`0x40581C` / `0x6C4090` 与两个虚调用）。消息「稍候再交易」「再交易」各 0 命中。

**唯一真实存在的 tick 门是提交阶段的 `dwDealOKTime`**（`sub_6C4580` 内，
C# `ClientDealEnd`，TRADE-20 已判 FAITHFUL）—— 那道保留不动，别混为一谈。

因为它是四道门里唯一有活运行期效果的一道，**单独成一次提交**，
主控若不接受可以只回退这一个 commit，不影响其余七个。

`m_DealLastTick` 字段保留（`dwDealOKTime` 门与 `ClientDropItem` 的 `> 3000` 仍在用）。
`g_sPleaseTryDealLaterMsg` 变为无引用，未删（不动 `M2Share.cs`）。

### 门 C/D — `m_boCanDeal`（自己侧 + 对端侧）→ **保留并标注**（提交 `e8563f38`，纯注释）

上一轮的理由「`m_boCanDeal` 在 `ClientClickNPC` 另有消费点」——**这条理由本身有毛病**，
但结论仍然是保留，理由要换成正确的那个。

**先说毛病**（§4.6 那类「引用的 VA 其实在说别的事」）：
`ClientClickNPC`（`TPlayObject.cs:1204`）里的 `if (!m_boCanDeal)` 占的正是原生
`0x6B8B4D cmp byte [ebx+0x461],0 / jne 0x6B8C84` 那道门的位置。
原生 `sub_6B8B28` 全函数**没有任何 `m_boCanDeal` 形状的字节**。
所以「它在 ClientClickNPC 另有活消费点」说明的是**又一处 INVENTED**，
不是「它有原生依据」。真正缺的那道 `+0x461` 门已由提交 `440e70ce` 补上（§3.3）。

**正确的保留理由**：`m_boCanDeal` 是**密码锁族**九项之一。
`TPlayObject.Base.cs:1396-1408` 在同一个 `if` 里整族设定
`m_boCanDeal` / `m_boCanDrop` / `m_boCanUseItem` / `m_boCanWalk` / `m_boCanRun` /
`m_boCanHit` / `m_boCanSpell` / `m_boCanSendMsg` / `m_boObMode`，
外加 `@LOCKLOGON` / `@PASSWORDLOCK` / `@UNLOCKSTORAGE` 等 GM 命令。
整族在镜像里都不存在（`密码保护系统` / `仓库已被加锁` / `开锁密码` /
`输入正确的密码` 全 0 命中），所以**正确的处置对象是整族，不是交易这两行**。
只删两行会把一个整族功能改成半残，比保留更糟，且属 §4.3 夹带。

**保留的代价可证为 0**：构造函数 `Base.cs:876-883` 把族内各项全部置 `true`；
唯一的置 `false` 入口要求 `boPasswordLockSystem && boLockHumanLogin &&
m_boLockLogon && m_boPasswordLocked`，而 `boPasswordLockSystem` /
`boLockHumanLogin` / `boLockDealAction` 均只有 `GameSvrConfig.cs:1215-1219`
一处 `= false`、无读取器 —— 恒 `false`。故 `m_boCanDeal` 运行期恒 `true`，两门恒不触发。

**移交**：整族的去留应另开一次「密码锁族」专项裁决，同时处理
`ClientClickNPC` 与 `ClientTakeBackStorageItem` 的 `m_boCanGetBackItem`（TRADE-55）。

## 3. 三处 MISSING 的「交易中拒绝」门

原生用同一个字段 `+0x461`（`m_boDealing`）在三处拒绝，C# 三处都没有。

### 3.1 存仓 `sub_6C2A34` @ `0x6C2AAC` → `ClientStorageItem`（提交 `85835d01`）

```
0x6C2AAC  80 BB 61 04 00 00 00  cmp byte [ebx+0x461], 0
0x6C2AB3  0F 85 3B 02 00 00     jne 0x6C2CF4
```

失败出口 `0x6C2CF4` 逐字节：`80 7D F5 00 cmp byte [ebp-0xB],0`（成功标志，此路仍 0）
/ `75 1B jne` / `66 8B 45 F6 mov ax,word[ebp-0xA]`（容器号，普通仓库恒 0，
由 `0x6C2A65 66 C7 45 F6 00 00` 初始化）/ `33 C9 xor ecx,ecx`（Recog=0）
/ `66 BA BF 02 mov dx,0x2BF` = `SM_STORAGE_FAIL`。

位置：容器分派（`0x6C2A6B` 的 wParam switch）之后、NPC 门（`0x6C2AB9`）之前，
三个容器共用。C# 补在支付检查之后、`FindMerchant` 之前，同序。

**玩家可见后果（修复前）**：交易托管进行中可以把背包物品同时存进仓库。

### 3.2 取仓 `sub_6C2D7C` @ `0x6C2DBC` → `ClientTakeBackStorageItem`（提交 `3e199046`）

原生开头连着两道门，C# 只有第一道：

```
0x6C2DAF  80 BB 83 06 00 00 00  cmp byte [ebx+0x683], 0   ; C# m_boCanGetBackItem
0x6C2DB6  0F 85 1F 02 00 00     jne 0x6C2FDB              ; → mov esi,-3
0x6C2DBC  80 BB 61 04 00 00 00  cmp byte [ebx+0x461], 0   ; m_boDealing   ← C# 缺
0x6C2DC3  0F 85 0B 02 00 00     jne 0x6C2FD4              ; → mov esi,-2
```

```
0x6C2FD4  BE FE FF FF FF        mov esi, 0xFFFFFFFE
0x6C2FE0  85 F6 / 7F 1B         test esi,esi / jg 0x6C2FFF
0x6C2FEF  8B CE                 mov ecx, esi              ; Recog = -2
0x6C2FF1  66 BA C2 02           mov dx, 0x2C2             ; SM_TAKEBACKSTORAGEITEM_FAIL
```

`Recog = −2` 是这道门自身的可观测输出，随门一起补上。
TRADE-45 讲的 `−1`/`−3` 属其它出口，本轮未一并回填（那是独立项）。
插入位置在 `m_boCanGetBackItem` 之后，与原生 683→461 的次序一致。

### 3.3 点 NPC `sub_6B8B28` @ `0x6B8B4D` → `ClientClickNPC`（提交 `440e70ce`）

```
0x6B8B4D  80 BB 61 04 00 00 00  cmp byte [ebx+0x461], 0
0x6B8B54  0F 85 2A 01 00 00     jne 0x6B8C84
```

这是 SEH 序言（`0x6B8B4A`）之后的**第一条**可执行语句。

**玩家可见后果（修复前）**：交易托管进行中可以点开 NPC 对话并触发脚本。
这条与 §2 的门 C 是同一个位置的两件事，注意别弄混。

## 4. TRADE-39 `FindMerchant` → `m_NPC`：只做收紧半，放宽半移交

用户点名这一项「两条路都超授权」。我的处置是**把它拆成两半，只落无争议的那半**。

### 4.1 已落地的收紧半（提交 `95046761`）

原生存仓：
```
0x6C2AB9  8B B3 D8 0C 00 00  mov esi,[ebx+0xCD8]   ; 玩家自持的 m_NPC
0x6C2ABF  85 F6              test esi,esi
0x6C2AC1  0F 84 2D 02 00 00  je  0x6C2CF4
0x6C2AC7  8B 83 D8 0C 00 00  mov eax,[ebx+0xCD8]
0x6C2ACD  3B 45 FC           cmp eax,[ebp-4]       ; msg.Recog
0x6C2AD0  0F 85 1E 02 00 00  jne 0x6C2CF4
```
取仓 `0x6C2DC9`/`0x6C2DCF`/`0x6C2DD1`/`0x6C2DD7`/`0x6C2DDD`/`0x6C2DE0` 完全同形，
失败出口 `0x6C2FE0` 处 `esi` 仍是入口 `0x6C2DA6 33 F6` 的 0，故走 **Recog = 0**。

`[ebp-4]` 的来源已钉死：分派桩 `0x6D91ED 8B 10 mov edx,[eax]`（opcode 1031）与
`0x6D922E`（1032）取的都是 `msg.Recog`（`[msg+0]` dword）。

**C# 侧的参数对位已逐层验证**（不是想当然）：
`UsrEngn.cs:2629 SendMsg(PlayObject, DefMsg.Ident, DefMsg.Series, DefMsg.Recog,
DefMsg.Param, DefMsg.Tag, sMsg, payload)`，而
`TBaseObject.cs:3526 SendMsg(BaseObject, wIdent, wParam, nParam1, nParam2, nParam3, ...)`
→ `wParam = Series`（容器选择，对应原生 `word[msg+0xA]`）、
**`nParam1 = Recog`**、`nParam2 = Param`（`word[msg+6]`）、`nParam3 = Tag`（`word[msg+8]`）。
`MakeLong(nParam2, nParam3)` 与原生 `0x6D91DF ax=word[msg+6]` /
`0x6D91D8 dx=word[msg+8]` / `call 0x408D40` 一致。

语义是「必须先点过、且点的正是这一个 NPC」。C# 原先只有 `FindMerchant` 全局查找 +
同图 + 距离，缺这条绑定：**伪造包在从未点过任何 NPC 的情况下也能开仓库**。

这半是**纯收紧**（只会拒绝更多请求，不会放行任何原本被拒的），所以可以单独落。
形状照抄本仓库里已判正确的账号仓库路径
`TPlayObject.NativeAccountStorage.Operations.cs:196-200`。

**新门不会误拒合法路径**（我查了）：原生对 `+0xCD8` 的写只有
`0x6B8BA7`、`0x6B8C48` 与属性设值器 `0x63DFAC`
（`55 8B EC / 89 82 D8 0C 00 00 mov [edx+0xCD8],eax / E8 3A 4C 13 00 / 5D C3`）。
C# `ClientClickNPC:1227` 覆盖前两处，其余脚本/商城/魔塔路径各自有 `m_NPC = npc`。

### 4.2 移交的放宽半：`m_boStorage` / `m_boGetback`（BLOCKED-授权）

**字节事实**：`sub_6C2A34`（`0x6C2A34..0x6C2CF4`）与 `sub_6C2D7C`
（`0x6C2D7C..0x6C2FE0`）内**完全没有**对 NPC 对象的任何布尔位测试。
对 `esi`/`edi` 指向的 NPC 只读 `+0x128`（地图）并传给 `0x7743E0` 算距离。
用户给的前提属实。

两条路的后果：

| 方案 | 效果 | 风险 |
|---|---|---|
| **删** `m_boStorage`/`m_boGetback` | 逐字节等价原生 | 任何点过的 NPC（含任务 NPC）都能当仓库用。这是原生行为，但 C# 现在挡着，删 = 主动放宽收包侧校验 |
| **留** | 比原生严 | 是一处 INVENTED 收窄；且与本轮补的 `m_NPC` 绑定叠加后，`merchant == null`（点的是非商人 NPC）会走 C# 拒绝而原生放行 |

**我的建议：删，但要单独一次提交、单独一次评审。** 理由：
1. 原生此处**确实无门**已逐字节确认，判定强度足够；
2. §1.4 的收包侧要求是「不得比原生**松**」，本项目一贯把「比原生严」也当偏离；
3. 但它不像 §4.1 那半是纯收紧 —— 它会**放宽**一个当前生效的限制，
   而放宽从来不该混在一个「补 MISSING 门」的提交里落地。
4. 落地前建议确认一件事：C# 的 `Merchant` 与 `NormNpc` 是两个类型，
   删掉 `m_boStorage` 后 `ClientStorageItem` 还需要 `Merchant` 类型吗？
   若不再需要，应改成 `m_NPC` 直用（无强转）；**不要为了保留 `m_boStorage`
   而对 `m_NPC` 做 `as Merchant` 强转** —— 那会把「非商人 NPC」这一路悄悄改成拒绝，
   等于换个写法把同一个 INVENTED 留下。

在授权到位之前，现状（保留 + 已加绑定）是安全的：只严不松，不丢物。

## 5. TRADE-53 数量字段：BLOCKED（提交 `70964c14` 只写注释）

用户的提示属实，且我把它推到了更强的结论：**不仅不能复用
`GetGameDataLogQuantity`，而且现在也补不了。**

### 5.1 原生形状

```
正向 0x6C47B2  80 7E 14 07     cmp byte [esi+0x14], 7      ; esi = 该 TUserItem
     0x6C47B6  75 3B           jne 0x6C47F3
     0x6C47BC  0F B7 46 26     movzx eax, word [esi+0x26]  ; ==7 → 数量 = Dura
     0x6C47F7  6A 01           push 1                      ; !=7 → 数量 = 1
镜像 0x6C48DA / 0x6C48E4 / 0x6C491D 完全同形
存/取仓共用日志块 0x6C2C68 / 0x6C2C72 / 0x6C2C99 也是同一形状
```

`+0x14` 是 **item 自身**的字节：同一函数取 StdItem 走的是
`sub_784568 @0x784573 8B 53 1C mov edx,[ebx+0x1C]` —— `+0x1C` 才是 StdItem 指针。
（顺带确认 `+0x26` = Dura、`+0x28` = DuraMax，由 `0x784584..0x784596` 的
`cmp dx,cx / jbe` 钳制对与 `0x7845A0`/`0x7845A8` 两个取值器共同确认。）

### 5.2 为什么判 BLOCKED 而不是直接补

`+0x14` 无法映射到任何现有 C# 字段，也**没有证据支持它等于 `StdItem.StdMode`**：

- 物品基类构造器 `sub_783788`：`0x7837AE C6 43 14 00` 写 **0**，
  而且发生在 `0x7837BA 89 73 1C`（存 StdItem 指针）**之前**，全程未读 StdItem 任何字段。
- 各子类构造器各自**硬写常量**：`0x784D67 C6 47 14 01`、`0x787CB5 C6 46 14 04`、
  `0x788C01 C6 47 14 07`（紧接 `0x788BFB 66 C7 47 26 01 00` 即 Dura=1）、
  `0x761A96 C6 47 14 01`。形态是「对象种类标签」，不是 StdItem 的镜像。
- **不落盘**：背包序列化 `0x6B1712 mov ecx,0x34` / `0x6B1717 rep movsd` 拷的是
  `item+0x20` 起的 208 字节，`+0x14` 在其之前 —— 纯运行期字段。
- 全镜像 `cmp byte [reg+0x14], imm8` 共 146 处，立即数直方图
  `{7:63, 0:18, 4:17, 3:15, 1:5, 2:4, 8:1, …}`，与「小整数种类枚举」相符，
  但不足以定名，也无法反推 C# 该用哪个字段。

凭这些去新增一个 `TUserItem` 字段并猜它的赋值点，属臆造。**fail-closed，不做。**

### 5.3 现状为什么是安全的

C# 两处交易日志的数量硬编码 `'1'`，**正好等于原生 `!=7` 分支**。
对所有 `+0x14 != 7` 的物品逐字节一致；只有那一类物品的数量偏小。
这是日志字段偏差（INTERNAL），不影响任何物品或金币的实际增减。

### 5.4 顺带推翻一条现有结论（本轮未改代码）

`NativeAccountStorageClient.GetGameDataLogQuantity`（`:61-66`）是
`stdItem.StdMode == 7 ? item.Dura : 1`，并由
`AuditTools/NativeAccountStorageCompatCheck/Program.cs:294-298` 钉住
（`stdItem.StdMode = 7` → 期望 37）。

但原生账号仓库走的**正是** `0x6C2C68` 那个三容器共用的日志块，读的也是
`byte[item+0x14]`，不是 StdItem 的任何字段。
**该审计工具钉住的契约同样未经证实。** 前序报告 §3.12 说
「`NativeAccountStorageClient.cs:65` 的 `StdMode == 7 ? Dura : 1` 恰好是原生那个形状，
可直接复用」—— 这句话是错的，照它做会把一个未证实的映射扩散到交易路径。

我没有改它：在 `+0x14` 的语义定死之前，改成什么都是猜。
建议把它和 TRADE-53 合并成一个「`item+0x14` 语义」专项。

## 6. 物品守恒论证

本轮**没有引入任何丢失或复制窗口**。逐条论证：

### 6.1 三处新增的 `+0x461` 门（§3）

三处都是**前置拒绝**：

- `ClientStorageItem`：门在 `for (i = m_ItemList.Count-1; ...)` 循环**之前**，
  在 `m_StorageItemList.Add` / `m_ItemList.RemoveAt` 之前。命中即整笔不发生。
- `ClientTakeBackStorageItem`：门在 `for (i = 0; i < m_StorageItemList.Count; ...)`
  之前，在 `AddItemToBag` / `m_StorageItemList.RemoveAt` 之前。同上。
- `ClientClickNPC`：门在 `normNpc.Click(this)` 之前，不触碰任何物品容器。

「删物不给」需要在删与给之间返回 —— 三处都在**删与给都还没开始**时返回，
不存在中间状态。「给物不扣」同理。

另外这三道门是**收紧**，收紧只会让整笔操作不发生，不可能凭空生成物品。

### 6.2 §4.1 的 `m_NPC` 绑定门

同上，两处都在循环之前。且是纯收紧（原来放行的请求现在可能被拒，反之不可能）。

### 6.3 门 B（删 `dwTryDealTime`）

`ClientDealTry` 函数体内**不移动任何物品或金币** —— 它只决定是否调用
`OpenDealDlg`。`OpenDealDlg` 内的 `GetBackDealItems`（原生 `0x6C40B8`，
TRADE-05 FAITHFUL）是把托管物**退回背包**的「给物」方向，不存在删物不给。

放宽节流的唯一二阶效应是提高该退回路径的频率。前序报告 R1
（背包 >48 时 `GetHumData` 越界抛异常 → 存盘持续失败 → 跨账号净增加）
**已由 TRADE-31 的 48 上界修复关闭**（`64baf93a`，已在基线内），
所以这条放大链现在是断的。

### 6.4 门 A1 / C / D

A1 删的是恒 `false` 的布尔析取项；C/D 是纯注释。运行期字节码等价，无守恒面。

### 6.5 剩余风险（本轮未引入，仅记录）

`GetBackDealItems` 仍无背包余量检查（TRADE-18，忠实复刻原生），
背包可以超过 48；存盘按 TRADE-31 静默截断到 48 —— **这会丢物，但与原生同向**，
是复刻的缺陷不是新缺陷。不要「修」它。

## 8. 我在复核中发现的前人结论错误

1. **配置键名扫描在本镜像上无效**（§1.1）。对照组 `ClickNpcTime` / `DealOKTime` /
   `SaveHumanRcdTime` / `TryModeUseStorage` / `GoldMax` **全部 0 命中**，
   而这些配置都有原生实现。任何据「配置键 0 命中」判 INVENTED 的推理对本镜像全部无效。
   有效的是 GBK 中文消息串扫描（对照组可证有效）。

2. **「`m_boCanDeal` 在 `ClientClickNPC` 另有消费点」不构成保留理由**（§2 门 C/D）。
   那个消费点占的正是原生 `0x6B8B4D` 的 `+0x461` 门的位置，
   原生 `sub_6B8B28` 全函数没有任何 `m_boCanDeal` 形状的字节。
   它说明的是**又一处 INVENTED**，不是「有原生依据」。正确的保留理由是密码锁族的完整性。

3. **「`dwTryDealTime` / `m_boCanDeal` 是配置化功能」不成立**（§2 门 B / C）。
   `GameSvrConfig.cs` 内 `ReadBool`/`ReadInteger`/`ReadString` 命中数为 0，
   `g_Config = new GameSvrConfig()` 直接构造，这三个配置运行期都是编译期常量。
   「配置化」是纸面上的，运营改不了。

4. **前序报告 §3.12「`NativeAccountStorageClient.cs:65` 的 `StdMode == 7 ? Dura : 1`
   恰好是原生那个形状，可直接复用」是错的**（§5.4）。
   原生读的是 `byte[item+0x14]`，与 StdItem 无关；照它做会把一个未证实的映射
   扩散到交易路径。相关审计工具钉的契约也未经证实。

5. **TRADE-45 的失败码要按出口逐个对，不能统一发 0**。本轮解出的完整码表：

   | 码 | 设置点 | 触发条件 |
   |---|---|---|
   | `0` | 入口 `0x6C2DA6 33 F6 xor esi,esi`（默认值） | NPC 门（空 / 不匹配 / 不同图 / 距离 >15）与物品查找失败 |
   | `−1` | `0x6C2FBC 83 CE FF or esi,0xFFFFFFFF` | 负重不足：`0x6C2EBD call 0x73C950 / test al,al / 0x6C2EC4 je 0x6C2FBC` |
   | `−2` | `0x6C2FD4 BE FE FF FF FF` | `+0x461` 交易中（本轮新补的门） |
   | `−3` | `0x6C2FDB BE FD FF FF FF` | `+0x683`（C# `m_boCanGetBackItem`） |

   注意 `−1` 那一路后面紧跟的 `0x6C2FBF cmp dword [ebp+8],3 / 75 1B jne` **不是**
   在限定失败码的适用容器 —— `−1` 对三个容器都成立；那条 `cmp` 只决定要不要
   多走一次 `0x6C2FCD call 0x414C24`（药品仓库的对象释放）。
   容易看成「−1 只属药品仓库」，实测不是。

6. **前序报告说 `sub_6C3F00` 有「6 道门」**，逐字节数是 **7 个条件分支**
   （`+0x461` / 前方空 / 前方是自己 / 对端前方非我 / 对端 `+0x461` / `+0x178` / `+0xBA0`）。
   前三条里有两条汇聚到同一个 `0x6C4015`，可能是被并成一条计数的。
   结论不受影响（都没有那四道额外门），但复核时按 7 个分支对。
