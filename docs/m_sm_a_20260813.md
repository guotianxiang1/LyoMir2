## 1. 复核中发现的前序结论错误（4 处）

### 1.1 【严重】`SM 0` 不是 wire ident —— `[obj+0xE0]` 过滤器在 VCL 类上失效

前序把 `+0xE0` 无条件当作发送槽。它对 TBaseObject 家族成立，但 `0xE0` 是一个**很低的 VMT 下标，
每个 Delphi 类都有**。全集里 `SM 0` 的两个"下发点"都在 VCL 窗体里：

```
00493387  6A00          push 0
00493389  8B4DF4        mov  ecx,[ebp-0xC]
0049338C  33D2          xor  edx,edx            ; <- 被当成 "mov dx,0"
0049338E  8B45FC        mov  eax,[ebp-4]
00493391  8B18          mov  ebx,[eax]
00493393  FF93E0000000  call dword ptr [ebx+0xE0]
```

`0x493338` 是构造函数（`0x49334E add esp,-0x10 / call 0x404A08` = `@ClassCreate`），
沿 SelfPtr 反查 VMT：

```
VMT 00795590  name=TSearchLogForm  instsize=0x30C  parent -> TForm -> TCustomForm
              -> TScrollingWinControl -> TWinControl -> TControl -> TComponent -> TPersistent
[VMT+0x0E0] = 00493510      ; 窗体自己的虚方法，不是 SendDefMessage
[VMT+0x250] = 2DE85AE8      ; 已经越过 VMT 尾部，不是代码指针
```

第二个点 `0x4991C4` 同形（同一 0x49xxxx 窗体区）。

**判据**：本区间 126 项里，只有 `SM 0` 的全部下发点落在 `< 0x600000`；其余 125 项的下发点
100% 在 `≥ 0x600000` 的游戏对象代码里。**原生 wire SM 全集应为 507（含 34）而不是含 0 的 507。**

### 1.2 【严重】`SM 34 (SM_NOWDEATH)` 被前序全集漏掉 —— 立即数装载形态不止 `mov dx/cx,imm16`

前序扫描器（`wire_audit/scan_sm*.py`）只认 `mov dx,imm16` / `mov cx,imm16`。死亡分发臂用的是
经 `ax` 中转的形态，因此整条被吞掉：

```
006B49CD  837B0C01      cmp  dword ptr [ebx+0xC],1   ; nParam3 == 1 ?
006B49D1  7506          jne  0x6B49D9
006B49D3  66B82200      mov  ax,0x22                 ; <- ident 34，前序看不见
006B49D7  EB04          jmp  0x6B49DD
006B49D9  66B82000      mov  ax,0x20                 ; ident 32
006B49DD  668B5304      mov  dx,[ebx+4]  / push edx  ; Param  = nParam1
006B49E2  668B5308      mov  dx,[ebx+8]  / push edx  ; Tag    = nParam2
006B49E7  668B5302      mov  dx,[ebx+2]  / push edx  ; Series = wParam
006B49EC  8B5324        mov  edx,[ebx+0x24]          ; 主体对象
006B49EF  8BC8          mov  ecx,eax                 ; <- ident 进 CX
006B49F1  8B45FC        mov  eax,[ebp-4]
006B49F4  E85B840000    call 0x6BCE54                ; CX 型包装器
```

生产网关计数器独立佐证：`srv_AppearTimes.ini` 里 **`34=18255061`**。
一个 1800 万次的线上 ident 在"原生全集"里缺席，这条本身就是扫描器完备性的红灯。

为把这类漏洞一次扫干净，本轮改用**目标优先**扫描（`q4_targetfirst.py`）：先枚举全镜像
**875 个** 发送槽/包装器调用点，再逐点反解 ident 寄存器；再补一遍**分支合流臂**
（`q5_altarm.py`）。结果：

- 目标优先扫描解出 507 个 ident，**前序全集里 ≤665 的项一个不漏地全部复现**；
- 分支合流臂在全镜像只多出 **1 项**，就是 SM 34；
- 生产计数器里 ≤665 的 ident 共 89 个，除 34 外**全部**已在全集内。

三条独立路径收敛到同一个结论，所以本区间的原生全集现在是闭合的。

### 1.3 前序的包装器清单缺 6 个（本区间无新 ident，但方法论要修）

前序手工列了 7 个转发包装器。本轮改成按字节判定（`q8_wrapdisc.py`：函数的 `edx`/`ecx`
形参不经改写或经入口 spill 到达发送槽），共找到 **13 个**，新增 6 个：

### 1.4 `RM_PHYSICAL_ATT` 的归属：REPLICATION_RULES §1.4 那句话只对了一半

规则文件写「`RM_PHYSICAL_ATT` 只是内部转发标签，真正下发的是 `SM_PHYSICAL_ATT = 1230`」。
后半句对（1230 确有 6 个原生下发点 `0x690DEE / 0x690F62 / 0x691040 / 0x6918B6 / 0x770E39 /
0x770E5A`，生产流量 5,724,002），**但这 6 个点一个都不在 RM 分发树里**。

原生 **RM 10612** 的臂是 `0x6B5D6C`，它发的是 **SM 70 (0x46)**：

```

006B5D6F  3B45FC        cmp  eax,[ebp-4]
006B5D72  0F84D4040000  je   0x6B624C           ; 是自己 -> 不发
```

本区间因此把 SM 70 登记为 MISSING 而不写代码（§4）。

## 2. 方法与解码基准

### 2.1 发送槽签名

沿用并独立复验了 m_sm2 §5.2 的签名：

```
[obj+0x250]  SendDefMessage(Self=eax, wIdent=dx, nRecog=ecx, Param, Tag, Series, sMsg)
[obj+0x254]  同上，末两个栈参换成 (Buf, Len)
[obj+0x0E0]  虚发送器，尾部多一个 (Buf, Len, boFlag)
栈参从左到右压栈：#1=Param #2=Tag #3=Series #4=sMsg|Buf #5=Len
```

本轮的两个独立复验用例（都是 C# 侧已判 FAITHFUL 的项）：

- `SM 545` `0x623A2E`：`Recog = byte[eax+0xAED]`，C# `SendDefMessage(SM_ATTACKMODE, m_btAttatckMode, 0,0,0,"")`
- `SM 653` `0x6B53F0`：`Recog = dword[eax+0x15C]`，C# `SendDefMessage(SM_GOLDCHANGED, m_nGold, 0,0,0,"")`
  （`[+0x15C]` 是金币字段，REPLICATION_RULES §4.6 已独立确认）

### 2.2 RM 记录布局

```
[rec+0x00] tag(word)   [rec+0x02] wParam(word)  [rec+0x04] nParam1
[rec+0x08] nParam2     [rec+0x0C] nParam3       [rec+0x10]/[rec+0x14] 串指针/长度
[rec+0x24] BaseObject
```

### 2.3 CX 型包装器 `0x6BCE54` 的完整语义（SM 6/7/9/10/11/13/27/32/33/34 全走它）

```
0x6BCE54(eax=接收方 Self, edx=主体 actor, cx=ident, [ebp+8]=Param, [ebp+0xC]=Tag, [ebp+0x10]=Series)
  006BCE6A  mov edx,0x20 / call 0x403B2C     ; 32 字节缓冲区 [ebp-0x24] 清零
  006BCE74  test ebx,ebx / je 0x6BCEB9       ; 主体为 nil 则整段跳过（缓冲区保持全零）
  006BCE7E  call [主体VMT+0x1C8](edx=接收方) ; -> [ebp-0x24] 头 4 字节
  006BCE88  lea esi,[主体+0x168] / 4×movsd   ; -> [ebp-0x20..0x11] 16 字节
  006BCEA2  call [主体VMT+0x70](edx=0, ecx=接收方, &[ebp-0x30])
            -> [ebp-0x10]=dword, [ebp-0xC]=dword, [ebp-8]=word
  006BCECC  push 0x20                        ; Len = 32
  006BCECE  mov ecx,ebx                      ; Recog = 主体 actor
  006BCED8  call [接收方VMT+0x254]
```

即：**这一族包的 body 恒为 32 字节的 actor 外观/状态描述，主体为 nil 时是 32 个零字节。**

### 5.2 为什么保留 `case Grobal2.RM_41:` / `case Grobal2.RM_43:` 的标签

`RM_41 = 9041`、`RM_43 = 9043` 都 **< 10000**，进原生分发器后
`0x6B3EF8 add eax,0xFFFFD8F0`（-10000）会绕成巨大的无符号数，被
`0x6B3EFD cmp eax,0x86 / 0x6B3F02 ja 0x6B6241` 打到 **default 静默丢弃**。

C# 这个 switch 的 `default` 不是静默的——它会走 `TryHandleNativeSocialProtocol` 再落
`base.Operate`。所以**留一个空 `case` 恰好复刻原生的静默丢弃**，删掉 `case` 反而把这两个
tag 改道到 default，属于额外行为变更。这与 m_sm2 §3 对 `RM_GAMEGOLDCHANGED` /
`CM_QUERY_FOCUS_ITEM` 的处置同理，也与 REPLICATION_RULES §5.1.6 一致。

另有一条硬约束：`AuditTools/TimedAbilityStateGateExactCheck/Program.cs:638` 把
`"case Grobal2.RM_41:"` 这段**源码文本**当作扫描区间的终止标记。按 REPLICATION_RULES §4.17，
不许为了让工具通过而弱化断言，但也不该把它变成找不到锚点的盲区——保留标签同时满足两边。

### 5.3 `SM_MOBILE_SURROUNDING` 为什么可以整块删

`SendMobileSurrounding` 在全树**零调用者**，`SendMobileStatusChange` 只被它调用。
按 REPLICATION_RULES「死代码算 MISSING」，这段运行期不可达；同时它做了两件违规的事：

- 自造 wire ident `0x3A (58)`，原生全集里没有；

## 10. 建议优先级

1. **SM 103 私聊字段修正**（§6.5）—— 唯一一个已完整解出、有线上流量、但本轮未修的协议缺陷。
   需要生产者与消费者一起改，建议单独一个任务，改完抓一次包验证。
2. **SM 627 / SM 56 / SM 625 功能层复刻**（269 万 / 278 万 / 41 万次）—— MISSING 里流量最高的三条，
   字段映射已在 §4 给全，缺的是玩家状态字节与列表容器。
3. **§7-B3 移动族光照字节**（合计 6 亿次）—— 改错代价最大，但也是影响面最大的悬案，
   建议先只做入队侧的取证，不要动代码。
4. **SM 106 / 626 / 213**（9 万 / 5.7 万 / 2 万次）—— 中等优先。
5. 其余 13 项 MISSING 线上零流量，可以排在最后。
