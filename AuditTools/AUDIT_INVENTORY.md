## Method and sampling rule

**No sampling was used for the mechanical columns.** All 376 projects were
parsed in full: sln membership, `OutputType`, line count, and assertion-call
count come from every file, not a sample.

The `purpose` column is extracted mechanically with a 3-step precedence, and
the source is labelled per row so you can judge how much to trust it:

| tag | source | count |
| --- | --- | --- |
| `c` | longest leading `//` comment run in the first 40 lines | 123 |
| `p` | the terminal `"PASS ..."` summary string | 123 |
| `a` | first assertion failure message | 125 |
| `-` | none of the above -> `UNKNOWN` | 5 |

`c` rows are authored intent. `p` and `a` rows are inferred from strings the
program prints, which describe what it checks but may lag the code. Rows
marked `UNKNOWN` are not guesses.

## Assertion counts are a weak proxy

The `asrt` column counts call sites of assertion-like helpers
(`Eq`/`Equal`/`Check`/`Assert`/`Require`/`Expect`/...) plus `throw new
*Exception`. **It measures how many times the program can say 'no', not
whether it checks the right thing.** A 200-assertion project that asserts a
C# constant against itself proves nothing; a 5-assertion project that
compares bytes against a native dump can be decisive. Treat the column as a
smoke signal for 'this file has no verdict logic at all', nothing more.

My first pass at this column was wrong in a way worth recording: a regex
covering only `Equal`/`Assert`/`Require` reported 6 assertion-free projects.
Four of them (`MonsterDomainRaceAndDropCheck`, `NativeStallManagerCompatCheck`,
`NativeStallStoreCompatCheck`, `SocialNamePersistCheck`) in fact assert heavily
through helpers named `Check(`, `Eq(` and `P(`. That was a false red caused by
the measuring instrument, not a finding.
